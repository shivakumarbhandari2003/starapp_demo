# Logics — how the important mechanisms work (and why)

Each entry: **what / how / why / where**. Use it to avoid re-inventing (or accidentally undoing) the optimisations from Stage 1 and 2.
Full "previous → new → reason" history: [WORK_DONE_AND_STATUS.md §6](WORK_DONE_AND_STATUS.md#6-change-log-append-here).

## A. Data layer & caching

| # | Mechanism | How it works | Why | Where |
|:-:|:---|:---|:---|:---|
| A1 | **DB fingerprint** | `PRAGMA data_version` + `conn.total_changes`. Any commit by any connection changes it. | Cheap, exact "did the DB change?" check, safe even with several processes reading. | `starapp/storage.py` |
| A2 | **Memoisation** | `_memoized(key, builder, extra, scope)`; entries valid while the fingerprint (scope `all`) or learning fingerprint (scope `learning`) is unchanged. `mark_dirty(learning=False)` marks feed-only writes so heavy caches survive notification/activity churn. | Dashboards/leaderboards were recomputed on every click (20–68 s at 3k users). | `storage.py`, used by `cycles.py`, `analytics.py`, `get_all_*` |
| A3 | **Secondary indexes** | `_ensure_ix(name, key_fn)` builds `dict[key] → list`, `_ix_commit` updates incrementally on every `save_*`. | Replaces `for x in all_items: if x.cosmonaut_id == …` (O(N) per call, O(N²) per page). | `storage.py` |
| A4 | **Lazy submission payloads** | `ProjectSubmission` keeps `pdf_payload`/`payload`/`code_payload` unloaded (`payload_is_lazy`) until `_hydrate()`; snapshots use `export_to_dict(include_blobs=False)`. | Base64 PDFs made the cache hundreds of MB. | `models.py`, `database.py` |
| A5 | **Feed rowid watermark** | `_sync_feed_tables` loads only rows with `rowid > last_seen` for `activity_events`/`notifications`. | No full reload for append-only tables. | `storage.py` |
| A6 | **Idempotent load** | `load_from_json` skips when `_loaded_data_version` equals the current version. | Removed the double reload on startup/new session (3.6 s → 1.8 s). | `storage.py` |
| A7 | **UPSERT, not REPLACE** | `INSERT … ON CONFLICT(id) DO UPDATE` in `save_user`, `save_cycle`, etc. | `INSERT OR REPLACE` deletes+reinserts → `ON DELETE CASCADE` wiped enrollments/roles/timelines (reproduced: 76 → 38 enrollments). | `storage.py`, `database.py` |
| A8 | **Safe writes** | `_write_failed` + `StorageWriteError` + `resync_from_database()` | In-memory state must never diverge from disk after a failed write. | `storage.py` |
| A9 | **30 performance indexes** | `PERFORMANCE_INDEXES` + `ensure_performance_indexes` run at start (idempotent) and `PRAGMA optimize`. | Covering the join/filter columns used by the grouped queries. | `database.py` |
| A10 | **Grouped export** | `export_to_dict` loads each child table once and groups in Python (no per-row queries). | Removed N+1 on startup/resync. | `database.py` |

## B. Appraisal & analytics

* **Cycle performance** (`cycles.py`): O(N) — every table is grouped once per cycle (by cadet / reviewer) instead of rescanned per person. Public
  `compute_cycle_candidate_performance` memoises the whole cohort per cycle and serves single-user requests from that cached cohort (`users_override`).
  Rows are returned as **copies** (callers may mutate).
* **Analytics** (`analytics.py`): cohort profiles memoised; dashboards use real data only — hard-coded demo names/dates/counts were removed
  (badge catalogue, trends, popover facts, `last_active`, `upcoming_deadline`, `band`/`track`).
* **Cohort definition** (`storage.get_all_cosmonauts`): users with cosmonaut role; guardians/admins excluded.
* **Leaderboard**: top-10 plus the viewer's own row.

## C. Rendering & UI engine

| Mechanism | Detail |
|:---|:---|
| **Regions** | `render()` produces `{sidebarHtml, topbarHtml, mainHtml, modalHtml…}`; `bridge.js::updateRegions` patches each if changed. Only **one render per action**. |
| **`_sidebarSignature()`** | Signature of the sidebar HTML with `class="nav-link active"` removed. Replace the `<aside>` only when the *structure* changes; otherwise `_updateSidebarInPlace` moves the highlight. (Root cause of the old flicker: active class made the HTML differ on every navigation → full `outerHTML` replacement.) |
| **`iconize_html(html)`** | Replaces emoji / glyphs (✓ ⚠ ★ ⚑ 🏆 📅 …) with inline SVGs from `get_icon`. Operates on **text nodes only**, quote-aware tag matching (so `=>` inside `onclick="…"` is safe), skips `<option> <textarea> <title> <script> <style>`. Applied to main content and modals in `app.py`. |
| **`humanize_internal_ids(text)`** | Replaces `m_b1_1`-style user ids with names and `badge_…` ids with badge codes; unknown ids are left untouched. |
| **Pagination** | `starapp/pagination.py`: `page_slice(items, key)` returns the page; `render_pager` draws it; `bind_page_state` binds page numbers to the request via a contextvar; action `set_list_page`. Used for cycles table, activity feeds (25/50 per page), dashboard roster/leaderboard. Mapping list capped (`MAPPING_LIST_DISPLAY_CAP = 60`). |
| **Bounded widgets** | Selector lists and the velocity chart are capped so page size doesn't grow with the cohort (Guardian dashboard 34 MB → 227 KB at 3k users). |
| **`cosmonaut_terms(html)`** | Final pass on sidebar / main / modal / page title / flash of every non-Guardian view: `cadet(s)` → `cosmonaut(s)` keeping case. Tokenised like `iconize_html` (text nodes + 4 text attributes only; skips `<script>/<style>`), so identifiers such as `rev_proj_cadet_ids` or `uncoupled_cadets` are never touched. Also rewrites stored activity/notification text. |
| **Rail cycle pill** | Guardian pillar pages only: short label (`C1`) in the 72 px rail, full code when expanded. The Cosmonaut sidebar no longer shows it - its band chip opens the cycle picker. |

## D. Server runtime & sessions (`backend/app/main.py`)

* `_run_dispatch` executes in a **threadpool under `_dispatch_lock`**, so the event loop stays free (static files, health, REST) while actions are serialised against the shared store.
* **Session registry**: `OrderedDict` LRU capped at `STARAPP_MAX_SESSIONS`; evicted sessions restore from the browser-held **signed snapshot** (`_sign_session_state`/`_verify_session_state`: HMAC-SHA256 with `SECRET_KEY`, includes expiry).
* GZip for responses ≥ 1 KB; restricted CORS; `HOT_RELOAD` (module reload per request) only in dev; `/js/starapp_bundle.js` only in demo mode.
* Health endpoint counts tables excluding `sqlite_%`.

## E. Workflow-logic details worth remembering

* **Project requests reuse `reviewer_project_prompts`** (no schema change): status `requested` / `fulfilled` rows are hidden from every project list (`get_reviewer_project_prompts(include_requests=False)`, `get_project_prompt_for_cadet`); `get_project_request`, `get_pending_project_requests(reviewer_id)` and `get_mapped_reviewer_id` are the accessors. One shared renderer `render_project_brief(title, content)` shows a project (big bold heading + pre-wrapped content) to both reviewer and cosmonaut; `_project_cta` decides Request Project / Project Requested / Submit Project Deliverables.

* **Allotment uncoupling:** after a pass, `store.uncouple_cadet_badge_mapping(badge, cadet)` removes the cadet from the active band mapping so the schedule shows them under *completed*, not *upcoming*.
* **Reviewer's cadets for a badge** (`_reviewer_cadets_for_badge`): union of timelines (`reviewer_id`), `band_mappings` containing the reviewer, and `badge.assigned_reviewer_id`. With several reviewers on a mapping, cadets are distributed round-robin (`rev_list[idx % len]`).
* **Roadmap state** (`roadmap.compute_milestone_state`): `completed` if approved; `active` if all prerequisites approved (or none); else `locked`. 25-milestone canonical order in `roadmap.CANONICAL_ORDER`.
* **Extensions:** approval rewrites `badge_timelines.submission_deadline` for that cadet+badge; everything is logged to `activity_events` + `notifications`.
* **Activity/notifications:** every workflow step calls `store.add_activity(...)` and `store.add_notification(...)`; feeds are cycle-scoped (`cycle_id`).
* **Closed cycle = read-only:** `handle_event` blocks state-changing actions unless in `_CYCLE_READONLY_SAFE_ACTIONS`.

## G. Known sharp edges (read before refactoring)

* Controller is large (6,000 lines, one `if/elif` action chain). Prefer adding small helper methods; keep action names stable (JS and tests reference them).
* `starapp/` is imported by the server **and** shipped to the browser (Pyodide). Avoid server-only imports in `starapp/` modules that the bundle needs.
* Tests call `store.reset_to_seed()`; that is why the runner isolates the DB. Don't write tests that assume the real DB's current contents.
* REST service layer ≠ controller rules (smaller duplicate). When a rule changes, change the controller and check the REST service.

## I. Reviewer badge review (Review Requests → one badge)
1. The Guardian's `send_badge_review_request` assigns the reviewer (badge `pending_review`). The reviewer's **Review Requests** page lists each requested badge as a **card** (title, skill lineage, Band, outcome / topic counts, sent-by / due, status); no Approve / Edit buttons on the card.
2. Clicking a card → `open_reviewer_badge_review` → page `c_badge_review` showing the REAL badge in the Guardian's structured format (`render_badge_document`, topics without learner progress controls). Only the badge's assigned reviewer (it is in their queue; Band ≥ B2) or a Guardian may open it; a stale / forged view id falls back to the queue.
3. **Edit** (`toggle_reviewer_badge_edit`) is allowed only while the badge is `pending_review` and `authorize_badge_decision` passes (assigned reviewer, Reviewer_Band > Badge_Band, not the author). **Apply Changes** → `save_reviewer_badge_edits`: needs a title + ≥ 1 outcome, no duplicate title in the same band/cycle; writes `title`, `description`, `learning_outcomes_json`, `learning_topics_json` (titles), `project_requirements` (practice prompt) and the whole structured `prompt_json` (+ `reviewed_by`, `reviewed_at`) through `store.update_badge_by_reviewer` → in-memory badge + SQLite + `badge_review_events` row `edited`; the creator (Guardian) gets a notification. Status stays `pending_review` — editing is not deciding.
4. Because the Guardian's *View Badge* (`view_saved_badge`) loads `prompt_json`, the Guardian sees exactly the reviewer's edits. Decisions: **Approve Badge** / **Return with Feedback** open the existing confirm modals; afterwards the page is read-only (an approved / returned badge cannot be edited).

### I.2 The 48-hour review window (every reviewer)
* `send_badge_review_request` stamps `badge_reviewer_assignments.review_due_at` = **now + 48 h** (full UTC ISO; `database.BADGE_REVIEW_WINDOW_HOURS`). The reviewer's request card and review page show a live countdown (`views_common.render_badge_review_timer` → `.rq-timer[data-sync="sync_badge_reviews"]`; `bridge.js` ticks it and dispatches `data-sync` at zero).
* **Sweep:** `StarAppController._expire_overdue_badge_reviews` runs at the top of every `handle_event` (like the 24 h mapping sweep) → `store.expire_overdue_badge_reviews` → `database.expire_overdue_badge_reviews`. A still-`pending` assignment whose deadline has passed becomes `expired`; the badge is **kept exactly as it is** (the reviewer's applied edits stay), goes back to `ready_for_review` with no reviewer, a `review_expired` audit event is written, reviewer + Guardian are notified. **Nothing is auto-approved**; the Guardian can send it again (fresh 48 h). Legacy date-only deadlines never expire.
* `authorize_badge_decision` also refuses a decision/edit after the deadline even if the sweep has not run yet. The reviewer keeps a **read-only** page (Read-only chip, no Edit / Approve / Return); an edit session that is open when the window ends drops back to read-only.
* Queue cards: title bold + larger (`.lg-sb-title.is-request`, a `div role=heading` so the `.app-main h4` pin does not shrink it), only the Band chip (no outcome / topic counts), the countdown replaces "Sent by"; decided / expired cards show a history-style line (`Approved · 27 Nov, 14:19 UTC`, feedback). Tabs: All / Pending / Approved / Returned / **Expired** / History. The queue joins only the reviewer's own, non-cancelled assignment, newest first.
* Reviewer "Cosmonaut Evaluation Invitations" are structured `.inv-card`s shown as compact cards in the same `.lg-allot-grid` as the badge cards, never as full-width expanded rows (title + band, status + 24 h timer, up to 3 cosmonaut chips + "+N more", review window with working-day count, actions).

### I.3 Cosmonaut privacy on the reviewer's invitation card
A reviewer's "Cosmonaut Evaluation Invitation" card shows only the badge name, Band, the live 24 h countdown (+ status / actions) and the review window. **No cosmonaut name or count is rendered** until all three hold: the request is **accepted**, the Guardian has **completed the mapping** for this reviewer, and the badge is **published**; then "Mapped Cosmonauts (N)" lists the cosmonauts actually mapped to this reviewer for the badge (`store.get_reviewer_mapped_cosmonaut_ids`: timelines + band mappings + badge assignment; first 3 named, rest "+N more"). A declined / expired request never shows them. The names are not in the HTML at all while hidden (not merely CSS-hidden).

### I.4 Publish -> 72-hour project window -> Project Allocated (cosmonaut)
* **Clock:** `publish_badge` stamps `badge.published_at`; from that moment every mapped reviewer has **72 hours** (`database.PROJECT_WINDOW_HOURS`) to create the project and send it to all their mapped cosmonauts. The publish notification says so. `storage.project_window_seconds_left(published_at)` (never negative; `None` when there is no publish time) feeds `views_common.render_project_window_timer` -> a live `.rq-timer` (`data-sync="sync_badge_reviews"`, ticked by `bridge.js`). The chip is shown on the reviewer's badge card while at least one mapped cosmonaut still has no project, reads **"All projects sent"** when none is left, and **"Project window ended"** after 72 h (display only - the reviewer can still send; nothing is auto-closed or auto-notified).
* **Reviewer page (Badge Reviews -> Upcoming Reviews):** one glass card per badge (code / band / status / "N projects to send", title, skill lineage, **Review window**, **Submission deadline**, **Project window**, ONE **Create Project** button -> `reviewer_project_creator` modal that sends to the mapped cosmonauts, and "N mapped cosmonauts"), then the cosmonauts in the Assessment Dashboard's connected-dot tree (`asm-tree-cosmo-list` / `asm-tree-cosmo-branch` / `asm-elbow` + `asm-cosmonaut-card is-static is-wide`): avatar / name / band / track, a status pill (Project pending / Project sent / Draft saved / Deliverables submitted / Evaluated n/50 / Retake required), the project title, the cosmonaut's own window / deadline only when they differ from the badge's, and Timeline / action / Assessments buttons.
* **Cosmonaut (Badges -> open a badge -> Earn the Badge):** there is **no Request Project** any more. The strip shows **Project Allocated**, **disabled** (`pa-btn is-locked`) until the mapped reviewer sends the project; then it **unlocks** (`pa-btn is-ready`) and opens the project **page** (`open_allocated_project_page` -> view `c_project`, see I.8) whose header holds **Submit Deliverables** (Edit Deliverables once submitted, Open marksheet once graded). `open_submission_modal` / `submit_project_deliverable` still refuse until a project was sent. The server action `request_project` is kept (legacy / tests) but no screen offers it.

### I.5 Reviewer Timeline modal
`render_reviewer_badge_timeline_modal` (Badge Reviews -> Timeline): the badge (code, band, title), three facts (Reviewer, Mapped cosmonauts, Projects sent n / N), the mapped cosmonauts as chips, then a **vertical timeline of connected dots** (`.tlv-*`: one continuous line, ringed dots, solid colours): Allocated & published -> **Project window (72 hours)** (range, live countdown, "All N projects sent" / "Window ended - n still to send") -> Learning period -> Project sprint -> Submission deadline (red) -> Review window (working days) -> Certification award; each step is Done / In progress / Upcoming from today's date (single-day events are Done or Upcoming). The schedule is read from the FIRST of THIS reviewer's mapped cosmonauts' timelines (falls back to the badge's default timeline) - it used to read a hard-coded cosmonaut. The Badge Review Schedule page no longer has the band chip / "Project Reviewer" label / Dashboard / Assessment Queue block (the title is hoisted into the Back strip).

### I.6 Project brief: synthetic sample + structured sections
* **Content format (no schema change):** a project is still *heading* + one text block (`reviewer_project_prompts.title` / `description`). The block is now written in sections - `Case Study`, `Your Challenge`, `Project Details` (bullets), `Deliverables` (bullets `Label: text`), `Evaluation` (bullets) - each heading on its own line, blank line between sections (`badge_generator.compose_project_content` / `parse_project_content`). Text without >= 2 of these headings is treated as free text and renders as before (old projects, tests).
* **Synthetic sample:** `badge_generator.generate_project_brief(badge)` builds a deterministic, realistic project from the badge's own skill, band, outcomes and topics (a named client scenario, a challenge, scope bullets, the three deliverables - PDF report / source code / GitHub repository - and the five 10-mark rubric criteria). The reviewer's Create Project form opens **pre-filled** with it (an earlier project is shown in the same fields; "Reset to sample" / "Load a fresh sample" refills from `data-sample`); the form shows every section **formatted** (paragraphs, bullet lists, deliverable icon cards, big heading) - **Edit** on a section swaps in its plain fields (`#rp-edit-*`), **Done** re-renders the formatted view from them (`bridge.js::toggleProjectSection` / `_pjRenderSection`); `bridge.js::submitReviewerProject` composes the fields (hidden or not) into the content block; the server action `send_reviewer_project` is unchanged.
* **Viewing:** `views_cosmonaut.render_project_brief` (cosmonaut project modal + inline "Your Project" card, and the reviewer's view) shows the big heading and then badge-style section cards (`cb-section-card` + icon chip); deliverables are three icon cards (`.pj-deliv`).

### I.7 Cosmonaut badge page (c_badge_detail)
* Built by `views_cosmonaut.render_cosmonaut_badge_page` from the SAME `render_badge_document` the Guardian / reviewer use (outcomes, earn strip, practice project, topics, resources, related; `location_label="Badge Location"`, `show_description=False`, `title_actions_html`) in glass. Removed: Back to Badges row, "Badge Workspace" line, code / band / "Project Allocated" chips, the description line, the assigned-reviewer / review-window / deadline banner, Back to All Badges, and the inline "Your Project" card. The page never shows the project: **Project Allocated** (disabled until sent) opens it, and Submit Deliverables lives only in that popup.
* **Reviewer | Timeline** buttons sit to the right of the badge name: `open_cosmonaut_reviewer_modal` -> `render_cosmonaut_reviewer_modal` (mapped reviewer, band / track, review window, submission deadline, project pending + live countdown / sent) and `open_cosmonaut_timeline_modal` -> `render_cosmonaut_timeline_modal` (the cosmonaut's own connected-dot timeline incl. "Project from your reviewer"; shared `_render_milestone_steps`). Both only for a badge allotted to the signed-in cosmonaut (`ActionDenied` otherwise).
* **Live updates:** the page and both popups carry `data-live-sync`; `bridge.js::startLiveSync` re-dispatches `sync_badge_reviews` every 6 s (only when a live page / popup is open, never under a modal that is not live, never while the tab is hidden); the server answers with the current store state and `updateRegions` skips the repaint when nothing changed - so "Project Allocated" unlocks and the reviewer / timeline popups refresh by themselves when the reviewer sends the project or the Guardian changes the mapping.
* Earned state: a glass "Badge earned & certified" card (allocated marks, evaluation chain, submitted deliverables, five rubric scores, evaluator feedback) above the document; retake state: a banner above it.
### I.8 Project page -> Submit Deliverables -> reviewer marks -> marksheet (cosmonaut) and Guardian
* **Project is a PAGE, not a popup.** `Project Allocated` dispatches `open_allocated_project_page` (the old `open_allocated_project_modal` / `view_allocated_project` names are aliases) -> view `c_project`. `StarAppController._allocated_project_denied(badge_id)` is the single guard for the action AND for `render()` (a stale session or crafted `c_project` falls back to the badge page / Badges): the badge must be allotted to the user and their project must have been sent. The Badges nav item stays highlighted (`activeNavId = c_submission`, `routeKey = c_project:<badge>`), the header Back returns to the badge page.
* `views_cosmonaut.render_cosmonaut_project_page`: header bar (code, badge name, PROJECT tag, status pill, ONE action: Submit / Edit Deliverables, or Open marksheet once the reviewer has graded), facts row (sent by, submission deadline, review window), the whole project (`render_project_brief`), and a "Your submission" glass card (attempt, time, the three files as chips, the marks once graded). `data-live-sync="project"`.
* **Submit / Edit Deliverables dialog** (`render_cosmonaut_submission_modal`, modal `submission_portal_modal`, class `modal-form` ~640 px): only the three deliverables (PDF report, source code, GitHub URL) as glass drop areas (`bridge.js::showPickedFile` shows the chosen file name), who receives it (the mapped reviewer), and the current files when editing. The project is NOT repeated. Submitting (`submit_project_deliverable` -> `execute_submit_project`, unchanged rules) closes the dialog, the cosmonaut stays on the project page, and the mapped reviewer is notified and sees it in Cosmonaut Assessments.
* **Marks.** The mapped reviewer assesses from the **Badge Review schedule** (the old Cosmonaut Assessments sidebar item and `c_assessments` page are gone; `nav_cosmonaut c_assessments`, a stale session and old notification links all land on `c_badge_reviews`). Each mapped cosmonaut row has ONE **Assessment** button (`rv-assess`): **disabled** (`is-locked`, dashed glass, tooltip) until that cosmonaut has submitted - a retake waits for the new attempt - then **enabled** (also once evaluated, to view the marks); no deliverables list on the card. It opens the workspace (`open_reviewer_assessment_page` -> `c_assessment_detail`, nav item Badge Reviews, Back to Badge Reviews) with the PDF / code / repo viewers and the 50-mark rubric (`submit_reviewer_assessment` -> back on the schedule). The Badge Reviews sidebar count = projects still to send + deliverables waiting for marks. `execute_submit_evaluation` now accepts the reviewer returned by `store.get_mapped_reviewer_id` (timeline -> band mapping -> badge's own reviewer) - the same rule as the project / submission routing and the assessment page (before, grading refused a reviewer that could open the page but had no timeline row). The cosmonaut gets a notification and the marks appear on `c_results` at once (live: `data-live-sync="marksheet"`, 6 s sync); the Guardian gets a "Reviewer Assessed" notification, sees "Ready for Sign-off" + the reviewer's score on the cosmonaut's card, and the reviewer's marks pre-fill the Guardian rubric. The Guardian's final decision adds a second marksheet (Guardian Official) and, on pass, awards the badge.
* **Marksheet UI** (`views_common.render_standard_marksheet`, shared by the page and the `marksheet_modal`): glass sheet = header (badge, attempt, evaluator + role, date, score ring from `conic-gradient`, percentage, outcome pill: Awaiting Guardian / Badge earned / Retake required), a note line, evaluation tabs (every attempt x reviewer / Guardian; `tab_action` = `view_marksheet` in the popup, `select_results_marksheet` on the page), five criterion rows with meters (green >= 8, blue >= 6, amber below), total, strengths / growth cards and the evaluator's summary. No tables, no inline navy header. `.ms-*` in `components.css`.
* **Marksheet page state** (`render_cosmonaut_results`): `cosmonaut_results_picked` (a badge chosen on the page) and `cosmonaut_results_asm_id` (the tab). Entering via the sidebar resets both, so the page opens on the badge with the newest evaluation; `open_badge_marksheet <badge>` (View marks / Official marksheet buttons) opens it on that badge; `select_results_marksheet` only accepts the user's OWN marksheets. Without a marksheet the page says where the work stands (submitted and waiting / project to submit / nothing yet) with the right button.

### I.9 Reviewer recommendation -> Guardian decision -> loop / gold badge
* **The reviewer RECOMMENDS, the Guardian decides** (the rule "reviewer grades, Guardian finalises" is unchanged). The reviewer's rubric panel (`render_reviewer_assessment_detail`) has three icon options - **Give Badge** (award), **Re-attempt** (refresh), **Reject** (x) - the shared `.lg-dec-*` component and `StarAppBridge.setReviewDecision`. Until the reviewer picks one themselves the selection follows the pass mark (`data-auto` / `data-thr`, updated by `recalcRubricTotal`).
* Stored on the REVIEWER marksheet's `decision`: `recommend_approve` / `recommend_resubmit` / `recommend_reject` (never `approve`, so analytics / earned checks can never mistake a recommendation for an award; legacy `reviewer_assessed` = marks only). `views_common.normalize_decision`, `REVIEWER_RECOMMENDATIONS`, `reviewer_recommendation_key`, `render_recommendation_chip`. Server rule: **Give Badge cannot be recommended below the badge pass mark**. The submission stays `reviewer_assessed` (nothing is awarded).
* **Marks are final per attempt.** Once the reviewer has submitted, a second submission for that attempt is refused ("locked") and the panel renders read-only (disabled inputs, the saved recommendation stays selected, a lock note instead of the submit button). A new assessment exists only for a new attempt (new submission id).
* **Guardian** (`render_guardian_review_detail`): a "Reviewer's recommendation" banner (chip + who scored what) above the marks; the decision control is pre-selected from the recommendation (else the pass mark); the drill-down card shows "Recommends: ...". The Guardian's chosen option now DRIVES the outcome in `execute_submit_evaluation` (before it was derived from the score only): **Earn Badge** (needs score >= pass mark, else refused) -> `approved`, timeline completed, mapping uncoupled, award activity + notification; **Resubmit** -> decision `resubmission_requested`; **Reject** -> decision `rejected`. Resubmit and Reject both set the submission to `retake_required` (the cosmonaut can start a new attempt); a passing score does not force a badge. No choice = the old pass-mark rule.
* **The loop restarts** on Resubmit / Reject: the cosmonaut's project page offers Submit Deliverables again (attempt + 1), the reviewer's Assessment button is locked until it arrives, then enabled for the NEW submission; attempt 1's marksheets stay on record. The marksheet shows Re-attempt / Rejected / Badge earned / Awaiting Guardian (+ the reviewer's recommendation in the note).
* **Gold badge (v2 styling).** The Badges card of an earned badge has no band / code chips or skill tree (any card): status chip, gold seal + name, Score / Awarded facts, a white-on-amber button. The badge page's achievement card shows the seal, "Achievement unlocked / Badge earned & certified", the final score and the five rubric scores with meters, and the evaluator feedback - nothing else (no awarded date, reviewer / Guardian chips or submitted files). Sheen animation respects prefers-reduced-motion. When earned (Guardian `approve`, `_cosmo_badge_state` / grid `is_earned`) the badge turns gold: `.gold-medal` (radial gold gradient, award icon) beside the badge name on the Badges card (card also gets a gold-tinted glass), on the badge page title (`render_badge_document(is_gold=True)`) and on the "Badge earned & certified" card. Fix: a Guardian marksheet no longer counts as "earned" by itself - only an `approve` decision does (a Resubmit / Reject sheet used to flag the badge earned).

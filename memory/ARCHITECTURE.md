# Architecture

## 1. Big picture

```text
Browser (index.html + js/bridge.js + js/api.js + css/)
   │  user clicks → StarAppBridge.dispatchAction(action, payload)
   │
   ├── POST /api/v1/dispatch  {action, payload, session_id}   ◄── main UI path (server-rendered HTML "regions")
   └── REST /api/v1/<feature>/…                                ◄── typed JSON API (js/api.js) for integrations/tests
                         │
                    FastAPI (backend/app/main.py)
                         │  GZip · CORS (restricted) · session cookie · rate of work serialised by _dispatch_lock
                         │
        ┌────────────────┴──────────────────┐
        │                                   │
 StarAppController (starapp/app.py)    REST routers (backend/app/features/*)
 one instance per browser tab/session   router → service → repository (parameterised SQL)
        │
 DataStore (starapp/storage.py)  ← ONE process-wide, in-memory, shared by all sessions
   • entity dicts + incrementally maintained secondary indexes
   • memoised aggregates keyed by a DB fingerprint
        │
 SQLite  data/starapp.db   (WAL, foreign_keys=ON, busy_timeout=5000, 30 extra performance indexes)
```

**Two execution modes of the same Python code**

1. **Server mode (default):** the controller runs in the FastAPI process; the browser receives HTML fragments.
2. **Offline/Pyodide mode:** `js/starapp_bundle.js` (generated by `scripts/pack_py.py`, 29 modules) embeds the same Python and runs it in the
   browser. Code detects it with the `IS_BROWSER` flag (`starapp/app.py`) and reads form fields from the DOM. The bundle endpoint
   `/js/starapp_bundle.js` is served only when `STARAPP_DEMO_MODE=true`. **Any change under `starapp/` requires rebuilding the bundle.**

## 2. Request lifecycle (UI path)

1. `bridge.js` calls `POST /api/v1/dispatch` with `X-Session-Id` (must match `_SESSION_ID_RE`; `default` allowed).
2. `main.py::dispatch_action` runs `_run_dispatch` in a **threadpool under a global lock** (actions share one in-memory store, so they are serialised).
3. `_run_dispatch` finds/creates the `StarAppController` in the **LRU registry** `_session_controllers` (cap `STARAPP_MAX_SESSIONS`, default 1500).
   If the session was evicted/restarted, state is restored from the **HMAC-signed snapshot** the browser sends back (`session_state`).
4. `controller.handle_event(action, payload_json)`:
   * gate: `action ∈ _GUARDIAN_ONLY_ACTIONS` and user not guardian ⇒ `ActionDenied` (logged `DENIED guardian-only action …`);
   * a big `if/elif action == "…"` chain mutates controller state and calls `store.*` writers; business rules raise `ActionDenied` or `set_flash(...)`;
   * read-only cycles (closed) block mutations except `_CYCLE_READONLY_SAFE_ACTIONS`.
5. **One render per action**: `controller.render()` builds `regions` (sidebar, topbar, main viewport, modal) via `views_*`; HTML passes through
   `iconize_html` (emoji → SVG) and `humanize_internal_ids`.
6. Response: `{success, regions, full_html (only if no regions), current_view, session_state (signed), user}`. `bridge.js::updateRegions` patches the DOM in place.

**Auth for the UI path:** login is an action (`login` / `select_demo_account`). The controller verifies credentials, validates `selected_role`
against `user_role_assignments`, and sets `current_user`. Navigation actions (`nav_guardian`, `nav_cosmonaut`) validate the target view
(`_GUARDIAN_VIEWS` / `_COSMONAUT_VIEWS`) and role.

## 3. REST path (`/api/v1/*`)

Routers: auth, users, bands, badges, reviews, allotments, submissions, evaluations, audit, cycles, gemini. Dependencies in
`backend/app/core/dependencies.py`:

* `get_current_user` reads the `starapp_session` cookie (HttpOnly, SameSite, optional `Secure`), touches `last_active_at` at most every 5 min.
* `require_roles(...)` (fixed in Stage 1): role aliases, roles read from `user_role_assignments`, really denies.
* Header/query identity shortcuts (`X-User-Id`, `?role=`) are accepted **only in demo mode**.
* `cycles` router: all mutations are guardian-only and the actor comes from the session (never from the request body).
* `GET /api/health` → `{status, database:{integrity, foreign_key_violations, table_count}, version}`.

> Note: the REST service layer duplicates a smaller subset of the controller's rules (see backlog item "unify services"). The UI/controller path is the
> richer and authoritative implementation of the workflow.

## 4. The controller (`StarAppController`)

* Holds **per-session UI state** (current view, selections, filters, modal, flash, page numbers, mapping wizard state, selected cycle …).
* Constants worth knowing: `_GUARDIAN_VIEWS` (19 ids), `_COSMONAUT_VIEWS` (16 ids), `_GUARDIAN_ONLY_ACTIONS` (37 actions), `_CYCLE_READONLY_SAFE_ACTIONS`.
* `execute_*` methods hold the heavy workflows: `execute_save_badge`, `execute_submit_project`, `execute_submit_evaluation` (reviewer *and* guardian
  grading), `execute_submit_extension_request`, `execute_extension_decision`, `execute_broadcast_announcement`, `execute_save_material/_bulk/update`.
* Rendering: `render()` → `render_login_view()` or a role view, plus `render_active_modal()`.
* Lists use `set_list_page` + `starapp/pagination.py` (page state kept in a contextvar bound per request).

### Views (ids)

Guardian: `g_dashboard g_cycles g_learning g_earning g_contribution g_create_badge g_badge_approval g_roadmap g_cosmonauts g_allotment g_badge_allotment g_mapping g_mapping_badge_detail g_reviews g_review_detail g_materials g_extensions g_announcements g_activity`.

## 5. DataStore (`starapp/storage.py`)

* Process-wide singleton `store`. Loads from SQLite once (`load_from_json` is idempotent via `_loaded_data_version`), then serves reads from memory.
* **DB fingerprint** = `PRAGMA data_version` + `conn.total_changes`. Any write by *any* connection changes it; memoised aggregates and indexes are
  invalidated lazily by comparing fingerprints.
* `_memoized(key, builder, extra, scope="all"|"learning")` — cached derived data (cohort profiles, cycle performance, leaderboards). `mark_dirty(learning=False)`
  distinguishes feed-only writes (activity/notifications) from learning-data writes so heavy caches survive feed churn.
* **Secondary indexes** (`_ensure_ix` / `_ix_commit`) — e.g. timelines by cadet/reviewer, submissions by cadet+badge, assessments by submission — maintained
  incrementally on each write.
* **Lazy submission payloads:** `ProjectSubmission` loads PDF/code blobs on demand (`payload_is_lazy`, `_hydrate`, `export_to_dict(include_blobs=False)`).
* **Feed tables** (`activity_events`, `notifications`) sync by rowid watermark (`_sync_feed_tables`) instead of reloading.
* **Write failures:** `StorageWriteError` / `_write_failed`; on failure `resync_from_database()` rolls memory back to disk truth.
* Upserts use `INSERT … ON CONFLICT DO UPDATE` (never `INSERT OR REPLACE` — see README §2).

## 6. Database layer (`starapp/database.py`, `backend/app/database/`)

* PRAGMAs: `foreign_keys=ON`, `journal_mode=WAL`, `busy_timeout=5000`.
* `PERFORMANCE_INDEXES` (30) are created by `ensure_performance_indexes` on first start (in place, idempotent, no data change); `PRAGMA optimize` runs.
* `export_to_dict(include_blobs)` builds the in-memory snapshot with grouped queries (no N+1).
* `authorize_badge_decision` guards `approve_badge` / `return_badge`.
* Health: `check_database_integrity()` ignores `sqlite_%` internal tables (so `sqlite_stat1` doesn't change the table count).

## 7. Front end

* `index.html` loads `css/`, `js/bridge.js`, `js/api.js` (and the Pyodide bundle in offline mode).
* `bridge.js`: `dispatchAction`, `updateRegions`, and **`_sidebarSignature()`** — the sidebar is replaced only on a *structural* change; the
  active-link highlight is patched in place (`class="nav-link active"` is ignored in the signature). This removed the flicker. Don't regress it.
* Icons: views may contain emoji; `iconize_html` converts them to the SVG icon set in text nodes only. Prefer `get_icon("name")` directly in new code.
* Styling vocabulary: shared `btn-metal` / `btn-secondary`, glass cards, WCAG-AA text colours (700-weight hues). Minimum font size 10 px.

## 8. Security architecture (summary — details in RULES_AND_CRITERIA §7)

HMAC-signed expiring session snapshots (key `SECRET_KEY`) · session-id regex · LRU session cap · constant-time compare · restricted CORS ·
`STARAPP_DEMO_MODE` gating · central guardian-only action gate · REST RBAC fixed · login role validation · upload size cap (`MAX_UPLOAD_CHARS`, ~9 MB).

## 9. Scalability design (summary — details in LOGICS.md)

Measured at ~3,000 users on a synthetic DB: cold start 1.8 s / 94 MB, new session ~15 ms, Guardian dashboard ~300 ms, cadet pages ~9–200 ms,
~70 req/s with 60 concurrent users, 0 errors. **Current ceiling:** one process, actions serialised — fine for thousands of registered users with
modest concurrency; scale-out needs the backlog items (shared session store, uploads out of SQLite).

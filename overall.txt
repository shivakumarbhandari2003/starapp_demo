1. EXECUTIVE SUMMARY & ARCHITECTURAL FOUNDATION
================================================================================
StarApp is an enterprise-grade training, gamified badge management, and skills
certification platform built for cohort-based engineering programs ("Batch Orion-24").

KEY ARCHITECTURAL HIGHLIGHTS:
- Zero-Backend WebAssembly Architecture: The application runs entirely inside the
  client browser without any traditional backend (no Node.js, Flask, FastAPI,
  Django, Supabase, or Firebase).
- In-Browser Python Execution: All application controllers, data access layers,
  rubric engines, cohort analytics, and UI templates are written in modular Python
  (Python 3.12+) and execute via Pyodide WebAssembly (v0.26.2).
- Zero Server Round-Trips for Business Logic: All calculations, evaluations,
  data mutations, and navigations occur in-memory within the Pyodide runtime.
- Multi-Tier Local Persistence: Data is persisted across IndexedDB (Database:
  "StarAppLocalDB", Store: "starapp_state", Key: "root_state") with fallback
  to localStorage. Session tokens are isolated per tab via sessionStorage, and
  cross-tab state changes are broadcast via BroadcastChannel.
- High-Performance 3-Region DOM Reconciliation: A lightweight (<970 lines)
  JavaScript bridge preserves UI focus and scroll states, patching only mutated
  regions (Sidebar, Main Page Slot, or Modal Root) rather than rebuilding the DOM.

2. TECHNOLOGY STACK & ZERO-BACKEND RUNTIME MODEL
================================================================================
- WebAssembly Engine: Pyodide v0.26.2 (CPython compiled to WASM)
- Core Programming Language: Python 3.12+ (executing inside Pyodide)
- Host JavaScript Layer: Vanilla ECMAScript 2022 (no React, Vue, Angular, or jQuery)
- Client Storage: IndexedDB API (Version 7) with localStorage fallback
- Session Isolation: Browser sessionStorage (enables simultaneous independent tabs)
- Real-Time Cross-Tab Sync: BroadcastChannel API ("starapp_cross_window_sync")
- Styling & Themes: Handcrafted modern CSS3 (Liquid Glass 2.0 / Glassmorphism)
- Static Launcher: Python built-in http.server (serve.py) with COOP/COEP headers
- Bundling Pipeline: scripts/pack_py.py bundles starapp/*.py into js/starapp_bundle.js
  which mounts onto Pyodide's virtual filesystem (/home/pyodide/starapp) at startup.

5. CENTRALIZED STORAGE & PERSISTENCE ARCHITECTURE (starapp/storage.py)
================================================================================
The DataStore class serves as the single source of truth for both portals.
Key implementation characteristics:
- In-Memory Dictionaries: Fast O(1) lookups for users, profiles, badges, timelines,
  submissions, assessments, materials, extensions, and announcements.
- Composite Keys: Timelines are indexed as "{badge_id}_{cosmonaut_id}".
- Schema Versioning: SCHEMA_VERSION = 10. Automatically triggers clean reset if
  older, incompatible schemas are detected.
- Dirty Marking & Serialization Cache: Calling mark_dirty() increments store.version,
  sets store.dirty = True, and invalidates store._cached_json. Read-only actions
  reuse the cached JSON string, avoiding expensive repeated serializations.
- Demo Reset Functionality: reset_to_seed() restores the clean initial baseline
  dataset (Dr. Elena Vance, Astraea Nova, 5 initial badges) without data corruption.

6. JAVASCRIPT BRIDGE & 3-REGION INCREMENTAL DOM ENGINE (js/bridge.js)
================================================================================
The JS bridge (~970 lines) provides the interface between browser APIs and Pyodide:
1. Storage Persistence:
   - Reads/writes state JSON to IndexedDB ("StarAppLocalDB", store: "starapp_state",
     key: "root_state").
   - Synchronizes fallback copies to localStorage.
   - Manages sessionStorage for per-tab credentials ("starapp_session").
2. Real-Time Cross-Window Synchronization:
   - BroadcastChannel("starapp_cross_window_sync") broadcasts mutations across tabs.
   - Tab-unique window ID (win_*) prevents echo loops.
   - Form Control Guard: If the user is actively typing in an <input> or <textarea>,
     incoming cross-tab reloads are deferred until focusout to avoid interrupting
     mentor evaluation or input entry.
   - Rapid-fire mutations within 300ms are coalesced into a single trailing reload.
3. 3-Region Incremental DOM Patching Engine (patchAppRegions):
   - Rather than wiping the entire DOM on every action (which causes scroll jumping
     and input focus loss), the UI is separated into three stable regions:
     * Region 1: Persistent Sidebar (#starapp-shell-sidebar). Link active states
       and notification pill badges are patched in-place. Sidebar re-rendering is
       skipped on standard page navigations.
     * Region 2: Main Page Content (#starapp-page-slot). Scroll positions and input
       focus are captured and restored. In g_review_detail, switching between PDF,
       Code, and GitHub tabs patches only .review-left-column while keeping the
       entire #guardian-rubric-form on the right untouched!
     * Region 3: Modal Root (#starapp-modal-root). When an open modal receives an
       update (e.g. live BroadcastChannel sync), title and body are updated without
       replaying CSS backdrop fade animations.
4. File I/O:
   - Reads local files as Base64 data URLs via FileReader API for client-side storage.

7. APPLICATION CONTROLLER, ROUTING & EVENT DISPATCH (starapp/app.py)
================================================================================
StarAppController coordinates authentication, view routing, modal states, and event
handling:
- Controller Initialization: initialize(stored_json, session_json) loads state from
  IndexedDB, restores active session, and mounts window.starAppController.
- Event Dispatch Method: handle_event(action, payload_json) decodes JSON payloads
  and dispatches them to specialized handler routines.

PRIMARY GUARDIAN ACTIONS:
- "nav_guardian": Routes Guardian between workspaces (g_dashboard, g_roadmap,
  g_allotment, g_mapping, g_reviews, g_materials, g_extensions).
- "set_guardian_cosmo_scope": Switches dashboard between cohort aggregate ("all")
  and individual cosmonaut dossier view.
- "set_guardian_risk_filter": Filters risk matrix table ("all", "on_track",
  "moderate_risk", "critical").
- "save_badge": Creates or updates a badge with title, code, category, prerequisites,
  and 9-point milestone dates.
- "toggle_badge_allotment": Toggles whether a badge is allocated to the cohort roadmap.
- "toggle_badge_publication": Toggles badge visibility to assigned cosmonauts.
- "open_review_detail": Opens deliverable evaluation workspace for a specific submission.
- "submit_evaluation": Validates and commits the 50-mark rubric marksheet, updates
  submission status (approve/reject/resubmission), and updates leaderboard averages.
- "decide_extension": Approves or rejects a deadline extension; upon approval,
  automatically updates the submission deadline across all platform timelines.
- "save_material" & "save_bulk_materials": Uploads single or bulk learning assets.
- "delete_material": Removes a learning resource.
- "broadcast_announcement": Sends batch-wide or targeted announcements.
- "guardian_mapping_*": Handles Band & Role mapping actions (band selection, role
  toggling, reviewer band selection, calendar date selection, request dispatch,
  accept/reject decisions, equal partitioning, and reset).
- "demo_reset": Resets all local data back to initial seed dataset.

MODAL SYSTEM:
Controlled via self.active_modal and self.modal_payload:
- "notifications": Displays list of system alerts.
- "badge_detail": Shows comprehensive badge details, requirements, and 9-point timeline.
- "marksheet_modal": Opens historical or audited marksheet with rubric breakdown.
- "material_preview": In-app viewer for PDF documents, YouTube lectures, and code.
- "review_submission": Quick-review modal dialog.
- "decide_extension": Extension approval/rejection modal.
- "create_announcement": Broadcast announcement authoring modal.
- "add_material" / "edit_material": Modal forms for adding/editing learning resources.
- "edit_badge": Modal form for creating/editing badge metadata and timelines.

9. BUSINESS LOGIC, VALIDATION & ANALYTICS ENGINES
================================================================================

9.1 Standard 50-Mark Rubric Engine (starapp/assessment.py)
- Criteria Bounds: Strict validation ensuring each score is a float between 0.0 and 10.0.
- Automatic Totals:
  total_marks = round(sum(5 criteria), 2)
  percentage = round((total_marks / 50.0) * 100.0, 1)
- Batch Leaderboard Ranking:
  * Fair average ranking: Computes mean percentage across approved badges only,
    preventing cadets with more badges from gaining an unfair advantage over cadets
    with higher scores on fewer badges.
  * Formats rank ordinal (1st, 2nd, 3rd...), total approved count, and average score.

9.2 Roadmap DAG & Milestone Progression Engine (starapp/roadmap.py)
- Directed Acyclic Graph (DAG) Validator:
  * Evaluates prerequisite dependencies before unlocking milestones.
  * A badge is "completed" if approved in an assessment marksheet.
  * A badge is "active" if all prerequisites are satisfied and it is published/allotted.
  * A badge is "locked" if any prerequisite badge is incomplete or unallocated.
- Dynamic Unlocking: When a mentor allocates a new badge, it replaces the current
  locked milestone, and the next unallocated curriculum badge becomes the new locked stone.
- Mathematical Winding Path: Generates coordinates for a 25-milestone serpentine
  curve connecting stone centers with cubic bezier SVG paths and pulsing halos.

9.3 Cohort Analytics & KPI Engine (starapp/analytics.py)
- Cohort Pacing & Velocity: Calculates expected milestones based on elapsed timeline days.
- Risk Classification Algorithm:
  * "On-Track": >=85% score average, zero overdue milestones, zero rejected submissions.
  * "Moderate Risk": Score average between 70-84%, or 1 overdue milestone.
  * "Critical / High Risk": Score average <70%, or >1 overdue milestone, or rejected attempts.
- Mathematical Popover Registry (get_kpi_popover): Provides exact formulas, numerators,
  denominators, and criteria for every KPI card in the dashboard.

9.4 Form & Domain Validation Engine (starapp/validation.py)
- validate_badge_input: Checks required code, title, and valid category.
- validate_timeline_dates: Verifies date ordering (Learning Start <= Learning End <=
  Project Start <= Submission Deadline <= Review Date <= Award Date).
- validate_submission_input: Checks deliverable payload and file format.
- validate_extension_request: Ensures proposed deadline is strictly after current deadline.
- validate_announcement_input: Ensures non-empty title, message, and valid targets.
